A security investigation conducted by cybersecurity firm **Claroc** has uncovered a widespread data leakage epidemic across applications built with generative AI: of **37,571 web applications** generated by Grok AI on the `grok.me` platform, **35,578 (94.7%) were found completely open to the public without authentication**.

The exposed applications were not just toy calculator demos. Researchers identified production tools containing confidential onboarding plans from social media network X and SpaceXSI (formerly xAI), patient medical records and ICU charts from hospital networks, internal shift schedules from emergency services, and contractor timesheet systems with **plain-text employee passwords** directly embedded in client-side code.

This discovery highlights a critical, systemic blind spot in the modern "vibe-coding" phenomenon: while AI models can rapidly assemble functioning UI layouts and rudimentary database calls, they do not inherently understand enterprise boundary security, database Row-Level Security (RLS), or secret lifecycle management.

If your startup, agency, or enterprise is adopting AI application generators or vibe-coding assistants to launch web tools, understanding why these exposures happen—and how to architect them safely—is paramount.

## The Illusion of Privacy: Why "Secret Links" Do Not Exist

Many users believed their generated tools were private because they had not explicitly shared the URL. However, the architecture of web infrastructure guarantees that unauthenticated URLs never stay secret:

```text
[ User Creates App via Grok AI Chat ]
                │
                │ (1) User clicks "Publish"
                │     Default access setting: "Anyone with the link" (pre-selected)
                ▼
[ App Deployed to Subdomain: `<word1>-<word2>-<word3>-<word4>.grok.me` ]
                │
                │ (2) First visit triggers DNS resolution & TLS handshake
                ▼
[ Public Reconnaissance & Discovery Engines ]
                ├─► Passive DNS (pDNS): Sensor networks record every queried subdomain
                ├─► Certificate Transparency (CT): Public logs index newly issued TLS certs
                └─► Search Engine Crawlers & Security Scanners
                ▼
[ Mass Exploitation & Public Ingestion ]
  • Over 35,000 apps indexed automatically without manual discovery
  • Attacker queries public endpoints: No sign-in, no session verification, no RLS
  • Reads and modifies customer database tables directly via client-side REST calls
```

### 1. Default Permissions: The "Anyone with the link" Trap
When users clicked "Publish" on Grok Build, the platform offered three privacy settings: *"Anyone with the link"*, *"Invited users"*, and *"Only you"*. Crucially, **"Anyone with the link" was pre-selected by default**. In contrast to platforms like ChatGPT's GPT builder (which defaults to private access), Grok apps immediately went live to the open web unless the user actively intervened.

### 2. The Fallacy of Random Word Slugs
Grok apps were assigned URLs based on four random words (e.g., `https://swift-timber-azure-falcon.grok.me`). While a four-word slug is computationally difficult to brute-force, it is **not secret once requested**. The moment a browser requests a domain:
- The DNS query traverses public recursive resolvers and is captured by **passive DNS** databases (e.g., Farsight, SecurityTrails).
- The automatic issuance of Let's Encrypt or platform SSL/TLS certificates publishes the hostname to public **Certificate Transparency (CT) logs**.
Anyone monitoring CT logs or querying passive DNS can retrieve every active `*.grok.me` subdomain in real time.

## Anatomy of the Architectural Failure: How AI Vibe-Coding Leaks Data

The research revealed that the vulnerability was not an exploit in Grok's underlying neural weights, but rather an **architectural deficiency** in how the AI generated software:

```text
                      FLAWED "VIBE-CODED" ARCHITECTURE
┌────────────────────────────────────────────────────────────────────────┐
│ Browser Client (React / HTML)                                          │
│   • Hardcoded Supabase / Firebase / Postgres Connection Strings        │
│   • Service Role / Admin API Keys baked into bundle (`NEXT_PUBLIC_...`)│
│   • Client calls database REST API directly:                           │
│     `fetch("https://api.db/users", { method: "GET" })`                 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Direct connection without auth
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ Database (Postgres / SQLite / Supabase)                                │
│   • Row-Level Security (RLS): DISABLED                                │
│   • Any anonymous visitor can read, insert, update, or drop tables     │
└────────────────────────────────────────────────────────────────────────┘
```

### 1. Missing Backend Authorization & Middleware
When prompted to *"create an employee contact directory"* or *"build an inventory tracker,"* AI code generators prioritize immediate visual fulfillment over layered security. The models frequently produce single-tier client applications where the frontend browser JavaScript talks directly to a cloud database (such as Supabase, Neon, or Firebase) without an intermediary authentication gateway.

### 2. Database Row-Level Security (RLS) Disabled
In tests conducted by Claroc researchers, when Grok generated a contact list application with an underlying database, anyone visiting the page from an incognito window could submit new database rows or view all previously submitted records. The database tables had **no Row-Level Security policies**, effectively turning the database into a public pastebin.

### 3. Plain-Text Secrets in Client-Side JavaScript
In several enterprise tools, AI models placed sensitive credentials directly inside frontend scripts:
- Hardcoded API tokens for OpenAI, Anthropic, Stripe, and SendGrid.
- Database service-role keys (which bypass all security policies).
- Internal company passwords stored in plain-text arrays in the HTML source to implement makeshift "login" checks using `if (password === "admin123")`.

## The Engineering Blueprint: How to Harden AI-Built Prototypes

AI coding tools are revolutionary for rapid prototyping and MVP creation. However, taking an AI-generated prototype to production requires professional software engineering rigor:

```text
                     SECURE ENTERPRISE ARCHITECTURE
┌───────────────────────────────┐
│ Browser Client                │
│ (Zero secrets, session-only)  │
└───────────────┬───────────────┘
                │ HTTPS + Authenticated HttpOnly Cookie / JWT
                ▼
┌───────────────────────────────┐
│ Serverless / Backend Gateway  │
│ (Node.js, FastAPI, Laravel)   │
│   • Session & RBAC Middleware │
│   • Input Schema Validation   │
│   • Rate Limiting             │
└───────────────┬───────────────┘
                │ Private VPC Network + Vaulted Credentials
                ▼
┌───────────────────────────────┐
│ Database (Postgres / MySQL)   │
│   • Row-Level Security: ON    │
│   • Least-Privilege Roles     │
│   • Automated Daily Backups   │
└───────────────────────────────┘
```

### 1. Decouple Database Queries from the Client
Never allow browser code to connect directly to databases with write permissions:
- Implement a **Backend-for-Frontend (BFF)** layer using Next.js Server Components, FastAPI, or Laravel.
- Keep database credentials strictly server-side, loaded via environment variables in an isolated server context.

### 2. Enforce Database Row-Level Security (RLS)
If using headless database platforms (such as Supabase or PostgreSQL):
```sql
-- Always enable RLS on every table
ALTER TABLE customer_records ENABLE ROW LEVEL SECURITY;

-- Restrict read access strictly to authenticated record owners
CREATE POLICY "Users can only read own data" 
ON customer_records 
FOR SELECT 
USING (auth.uid() = user_id);
```

### 3. Enforce Zero-Trust Authentication
- Do not build custom frontend password checks in JavaScript.
- Implement established identity providers: Clerk, Auth0, Supabase Auth, or standard OAuth2/OIDC.
- Protect all internal business dashboards behind Single Sign-On (SSO) with MFA.

### 4. Conduct Pre-Deployment Secrets Scanning
Incorporate automated secret detection in your deployment pipeline to catch leaked tokens before code goes live:
```bash
# Run Gitleaks or Trufflehog to scan for embedded credentials
gitleaks detect --source . --verbose
```
